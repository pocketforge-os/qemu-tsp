Reproduction
------------

Build QEMU at the head above, then run inside the pinned qemu-test image with
the four source artifacts mounted read-only:

  python3 tests/pocketforge-a133-build6-smoke.py \
    --qemu build/qemu-tsp/qemu-system-aarch64 \
    --dbus-listener build/qemu-tsp/pocketforge-a133-dbus-listener \
    --image /inputs/Image \
    --dtb /inputs/dtb.bin \
    --initrd /inputs/initrd.gz \
    --sd /inputs/Image.img \
    --work build/release-smoke/run

The smoke waits for the guest's systemd service stage. It records whether the
release image started `pf-input-decode.service` itself and starts that exact
unit only when inactive. On this run the unit was already active
(`decoder=auto`). The unrelated suspend path is masked on the QEMU-only kernel
command line. `pf-input-broker.service` is stopped only if active and restored
in the same invocation; it was inactive on this run.

Guest evtest evidence
---------------------

The harness opens the release-created `TRIMUI Player1` and `axp20x-pek` event
nodes as uid 1001. It sends a rejected EV_SW report to each QMP device, an
atomically accepted batch containing twelve explicitly framed gamepad reports,
and short- and long-duration power-key press/release pairs in the same QMP
session. The serial transcript contains:

The two power lines each occur twice: once for the short press and once for the
long press. The PMIC qtest separately asserts the AXP717 short/long status bits
against the DT-owned one-second threshold; Linux exposes both durations as the
same KEY_POWER edge pair, as expected.

No EV_SW/SW_LID line occurs. The harness asserts both the stable QMP error
prefix (`pocketforge-input: reason=invalid-parameter index=0:`), the exact
guest-reported ranges and identity, every event above, and absence of an EV_SW
guest record before reporting PASS. Timeout failures include the serial tail,
so a boot-order or guest-service failure cannot appear as a negative-control
success.

Native display proof (2026-10-13)
---------------------------------

The harness requires the unmodified release kernel's own `sun4i-drm` fbdev,
writes a magenta XR24 marker at native coordinate (0,0), and reads it from both
upstream Display1 `Console_0` and the same QemuConsole's screendump path. The
listener ignores the initial black Scanout, so only a post-modeset guest-RAM
update can pass. The serial transcript additionally proves the release mixer,
TCON-TOP, TCON-LCD, DSI host and OTM1289A panel component binds; completed DCS
panel prepare; no timeout attributed to a display component; and DRM vblank
delivery beginning with counts 1 and 2 (227 observed before completion).

The release Image, DTB, initrd and source raw image remained byte-identical.
The harness modified only its disposable raw-image copy and removed it at exit.

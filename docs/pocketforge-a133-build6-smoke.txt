Boot/QMP evidence
-----------------

The real build-6 tuple booted from the modeled MMC0 to systemd. QEMU appended
its two virtio-mmio nodes to the boot-time DT, but the exact kernel could not
bind either node. `query-pocketforge-input` continued to return `ready:false`.

The metadata query returned:

  profile=hardware native=720x1280 preferred_fourcc=XR24
  active_scanout=720x1280 stride=2880 fourcc=XR24
  plane_rotation=0 presentation_rotation=90

A GIO listener registered with `-display dbus` and received the copy-path
Scanout below. Its dimensions, stride and byte count match the query exactly;
pixman format 537004168 is `PIXMAN_x8r8g8b8`, the in-memory XR24 layout.

  DBUS_SCANOUT width=720 height=1280 stride=2880 format=537004168 \
    bytes=3686400 first=00000000

This proves the headless D-Bus frame and geometry portion of the smoke. The
initial frame is black, so it is not evidence that the guest bound
virtio-gpu; the kernel configuration independently proves that it cannot.

On a full boot of the same exact tuple, the required negative input control
behaved as ABI 1.0 specifies. The display and input diagnostics were separate
invocations; the missing guest drivers prevent the requested end-to-end
single-invocation smoke:

  request: type=5 code=0 value=1; SYN_REPORT
  result:  GenericError
  desc:    pocketforge-input: reason=invalid-parameter index=0: undeclared evdev type

A valid BTN_SOUTH report then returned:

  DeviceNotActive: PocketForge input guest driver is not ready

Consequently, no guest evdev node exists from which to read the negative or
positive events. Claiming either a D-Bus pixel frame or guest input readback
would be a false pass.
